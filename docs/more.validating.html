Validating

Documon derives structure only from your comments. That is its main strength — you
decide exactly what the output looks like — but it has one consequence worth naming: a
symbol you forget to tag doesn't produce a warning, it produces nothing at all. A
misspelled tag is discarded in silence.

--check is the antidote. It parses everything, tells you what won't work, and writes
nothing.

documon --check -i ./src

------------------
Findings
------------------
ERROR  src/menu.js:42
      [unresolved-inheritance] @extends "Base" does not match any documented id.
      fix: Use the fully qualified id (package.Class), or document the parent.
WARNING  src/menu.js:88
      [unknown-tag] @arg is not a Documon tag and will be ignored.
      fix: Use @param instead.
------------------
Summary
------------------
  files : 25
  comments : 117
  entities : 111
  errors : 1
  warnings : 1
  info : 6
FAIL

It exits 2 when it finds problems, so it drops straight into a build script:

documon --check -i ./src && documon -i ./src -o ./

What it looks for

rule level meaning
unknown-tag warning A tag Documon doesn't implement, and doesn't alias. Anything you wrote under it is dropped. The fix explains why there is no equivalent.
retired-tag error A spelling Documon used to accept and no longer does. Today that means @impliments. It used to work, so silence would look like success.
no-files error Nothing matched. Check the -i path and the -e extensions.
unreadable-file error A source file could not be read.
normalized-tag info A tag accepted under another spelling (@arg read as @param). Nothing is lost; shown so you can converge on one spelling.
duplicate-id error Two blocks resolve to the same id, so one page overwrites the other.
unresolved-inheritance error An @extends / @inherits / @implements target that matches no documented id. A bare name is resolved against the block's own package first, exactly the way the builder resolves it, so the same-package short form (@extends Base) is accepted.
missing-name error A kind tag with no name, e.g. a bare @method.
no-kind warning A block with tags but no @method, @property, @event, @class or @module. It will never appear.
param-no-name warning A @param that can't be rendered.
duplicate-param warning The same parameter documented twice.
param-on-non-method warning @param on @property, which never displays it. Methods, events, and the @class / @module that heads a page all render a parameter table.
broken-link warning A dotted cross-reference that matches no id. Ids from the more folder (more.options) count as valid targets, and the more markdown is checked too -- see below.
placeholder-doc warning Documentation left as an unfilled stub: a literal {type}, a description that is just the word "description", or a [name description] block.
no-description info A documented entity with no prose.
param-no-type info A parameter with no {type}.
no-comments info A source file with no Documon blocks at all.
undocumented-symbol info Emitted by --coverage for each symbol with no matching block.

--strict promotes warnings to failures.

Prose links are checked too

Point --check at your more folder and it validates the cross-references written in the
markdown, not just the ones inside source comments:

documon --check -i ./src -m ./more

A prose page linking to more.nosuchpage, or to an API id that has since been renamed, is
reported against the markdown file and line it was written on. This is where most
cross-linking actually happens, and a broken one is invisible until a reader clicks it --
the site intercepts the id, finds nothing, and does nothing.

Links inside code blocks are skipped, fenced and indented alike, for the same reason
@example content is skipped: a manual teaches the shape of an id with links that were
never meant to resolve.

This resolves, and is checked:  [the options](more.options)

    This is a teaching example, and is not:
    [see Foo](package.Class.method)

If your config file already sets more, you don't need the -m flag -- --check reads
the same configuration a build does.

Placeholders

An unfilled stub is worse than no documentation, because it renders on the page exactly as
written and therefore looks finished:

/**
 * [doThing description]
 * @method doThing
 * @param  {type} item  description
 */

Nothing else catches that -- no-description only fires on an empty block, and
param-no-type only on a missing type. placeholder-doc reports each distinct stub once
per block, so a heavily stubbed file produces a readable report rather than a wall.

Coverage

documon --check --coverage -i ./src

Adds an advisory pass that looks for functions, classes and assignments with no matching
documentation block, and reports a percentage.

This is the one place Documon glances at your source, and it is deliberately shallow and
strictly advisory — it never influences what gets rendered. Structure still comes from
comments and nothing else. If a symbol is intentionally internal, ignore the finding.

Machine-readable output

documon --check --json -i ./src

Emits a JSON report — ok, counts, stats, coverage, and a findings array where
each entry carries level, rule, file, line, message and fix. Useful in CI, and
useful to any tool that writes comments and needs to know whether it succeeded.
