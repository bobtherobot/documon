# Machine Readable Output

Alongside the HTML, every build writes three files intended for programs rather than
people. They cost nothing to generate and make your documentation usable as data.

## llms.txt

Follows the [llms.txt convention](https://llmstxt.org): a short markdown index naming
every page with a one-line summary, so a language model can find the right page without
crawling the site.

	# My Project v1.0

	> One line about the project.

	## Reference

	- [dirutils](https://example.com/docs/my.dirutils.html): Directory helpers.
	- [Menu](https://example.com/docs/my.Menu.html): The navigation tree.

Set `--baseUrl` to get absolute links; without it the links are relative.

## llms-full.txt

The whole manual as plain text — every page, every member, every parameter — in one file.
One fetch instead of dozens, with no HTML to strip.

## model.json

The documentation as structured data:

	{
	  "generator" : "documon",
	  "project"   : "My Project",
	  "version"   : "1.0",
	  "pages" : [
	    {
	      "id"      : "my.dirutils",
	      "name"    : "dirutils",
	      "kind"    : "module",
	      "package" : "my",
	      "description" : "Directory helpers.",
	      "members" : [
	        {
	          "kind"    : "method",
	          "name"    : "make",
	          "access"  : "public",
	          "params"  : [ { "name" : "dest", "type" : "string", "description" : "..." } ],
	          "returns" : { "type" : "boolean", "description" : "..." }
	        }
	      ]
	    }
	  ]
	}

Anything that wants to build on your docs — a search index, a linter, an editor plugin, a
coding assistant — should read this rather than scrape the HTML.

## Turning them off

	documon --no-emitLlms --no-emitModel -i ./src -o ./

Or in `documon.json`:

	{ "emitLlms" : false, "emitModel" : false }
